# 收尾策略：模型停手、验收门控与竞品对照

> 日期：2026-09-15  
> 状态：设计收敛（推荐方案 D′；部分解析/匹配修复已落地，主循环策略尚未按本文改）  
> 相关：`Harness-L2与Gate工作逻辑.md`、`src/harness/completion-gate.ts`、`src/harness/task-acceptance-tracker.ts`、`src/harness/harness-round-no-tools.ts`

本文回答三件事：

1. 为什么会出现「模型想停、门控不让停、任务空转」。
2. OpenCode / Claude Code / Codex 实际怎么结束一轮。
3. iceCoder 更合理的收尾策略是什么——以及哪些方案看起来更聪明、其实更差。

---

## 1. 现场：fusion-06 第 19～22 轮

任务 `debug-saas-order-supply-approval-fusion-06`，模型 `mimo-v2.5`，`reasoning=high`。

| 轮次 | 发生了什么 |
|------|------------|
| 16 | `npm test && test:integration && test:contracts && migrate:check && audit:snapshot && build` **成功** |
| 17 | 再跑 `npm ci`（成功） |
| 18 | `git diff --name-only -- test/ …` 失败（exit 129） |
| 19 | 模型给出最终总结，**不再调工具**（想停） |
| 20 | Completion Gate 注入续跑；模型写 `node -e`，被 Windows 内联脚本规则拦住 |
| 21 | 再 `npm ci` |
| 22 | 约 8.2 万 token + high reasoning 的 stream 空转，用户中断 |

会话 `1f7ef7b8` 里门控注入的原文大意是：`test/` failed、`README.md` pending、`tenantId` pending、公式 pending、`source of truth` pending……同时真正的 `npm test` / `npm ci` / `build` 等多数已经 satisfied。

结论：**业务已经可停；拦住它的是一份被 prompt 反引号污染的必过清单，外加 `git diff -- test/` 子串误伤。** 模型第 19 轮的判断是对的。

## 2. 当前 iceCoder 怎么决定「结束」

无工具轮（`harness-round-no-tools.ts`）大致顺序：

```
空响应 / 截断恢复
  → Stop Hook（模型自承「还要继续」时拉回）
  → CompletionGate.evaluate(条件 + 操作账本)
       continue → 注入 [System / Completion Gate]，再跑一轮
       pause/fail → 停，但不是 model_done
       complete → 还可能走 no-tool recovery
  → 无工具恢复（pending 交付物等）
  → model_done
```

`CompletionGate` 按固定优先级看：

1. required 条件 pending / failed / unverifiable  
2. 操作 pending / 待审批  
3. 未解除的失败  
4. 高风险缺回执  
5. 答案未就绪  
6. 否则 complete（可能是 `completed_unverified`）

验收条件主要来自 `TaskAcceptanceTracker`：从用户目标里的反引号 / 引号「编译」出命令列表，全部 `required: true`。长跑目标（含 `npm ci`、`从零实现` 等）且解析出 ≥2 条就会激活。

同一阻塞签名最多 continue **一次**（`canContinue`）。fusion 并没有在门控里死循环：只续了第 20 轮。后面空转是模型被脏清单带去「再检查禁止改的文件」。

## 3. 已落地的修复（仍不够）

针对第 1 节的脏清单，已经改了三处（2026-09-15）：

| 点 | 以前 | 现在 |
|----|------|------|
| 什么算验收命令 | 几乎任意反引号（路径、公式、短语） | 仅 runner 型命令：`npm` / `make` / `./scripts/ci.sh` 等 |
| `a && b && c` 成功 | 往往只更新第一条命中项 | 链上每一段对应项都标 passed |
| `git diff -- test/` 失败 | `includes('test/')` 把 `test/` 标 failed | 按命令段精确匹配，无关 diff 不再入账 |
| 续跑文案 | 「条件未结清，换一种检查」 | 「把还没过的验证再跑一遍，过了就停」 |

这能避免 README / tenantId 永久 pending。**主循环仍是：门控否决模型停手，且 7 条真命令仍是 7 个独立必过位。** 模型若只跑了 `npm test` 就总结，仍可能被拦住。

## 4. 竞品怎么做

### 4.1 Codex

[Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)（2026-01）：

- 有 tool call → 执行 → 把结果喂回模型。
- **模型改为只写 assistant 正文、不再发 tool call → 循环结束，把回合交还用户。**
- 正文就是终止态（例如 “I added architecture.md”）。
- Harness 负责沙箱、审批、压缩；**没有「从用户目标编译验收清单再否决停手」这一层。**

### 4.2 OpenCode

`packages/opencode/src/session/prompt.ts` 的退出条件（公开源码）：

- `finish` 不是 `tool-calls` / `unknown`，**并且**最后一条 assistant 里没有待执行的 tool part → `exiting loop`。
- 历史上只看 `finish_reason` 出过两类 bug：`stop` 时空转；部分网关在带 tool 时也返回 `stop` 导致早停。修复是 **finish + 是否真有 tool 一起看**。
- 没有贯穿全程的验收账本。压缩溢出是另一条 continue，与「任务没做完」无关。

### 4.3 Claude Code

默认循环与上面相同：**没工具就停。**

额外能力是可选的 [Stop hook](https://code.claude.com/docs/en/hooks)（默认关）：

- 模型结束回复时触发。
- 脚本可以 `block`，迫使再跑一轮。
- 输入里带 `stop_hook_active`：若已经因 hook 续过，**必须放行**，否则会死循环。
- 连续 block 有上限（文档称默认 8，可用 env 调）。

业界踩坑最多的就是：Stop hook 跑测试、不看 `stop_hook_active`、条件一直不满足 → 会话卡死。这和 fusion 第 19 轮是同一类失败：**用第二套判定否决模型停手，且判定与真实进度不同步。**

### 4.4 对照表

| | 默认何时结束 | 谁保证「测过了」 | 硬拦 |
|--|--------------|------------------|------|
| Codex | 无 tool call | 模型自己跑；prompt 里写 | 沙箱 / 审批 / 用户中断 |
| OpenCode | finish ≠ tool-calls 且无 tool part | 模型自己跑 | 同上 |
| Claude Code | 无工具 | 默认无；可选 Stop hook **跑脚本** | hook 最多顶有限次 |
| iceCoder 现在 | CompletionGate 说了才算 | 从 goal 编译命令列表，条条 required | 条件 / 失败 / pending / 缺回执 |

同模评测里 iceCoder 往往只比 CC 高约 1～3 分（公开 Gate 常一起绿）。厚收尾层几乎进不了 Judge 的 D1–D3，却能多烧十几轮。

## 5. 讨论过的方案

### A. 继续完善验收编译器

收紧解析、链式更新、禁止子串误伤——**已经做了。**  
再加 NLP、禁止修改段排除、白名单路径：解析器会继续膨胀，fusion 类长 prompt 永远有漏网。

### B. 把执行情况打包，再叫一次模型当法官

看起来「让模型判断结束」，其实多一次 8 万 token + high reasoning。  
第 19 轮主模型已经判断该停；同一模型再问一次，答案多半还是停。贵、慢、还可能再空转 stream。

**不采用。**

### C. 短回执给正在干活的那一轮，无工具即停

每轮给模型看十几行：改过的文件、上次编辑之后跑过的命令和 exit code、是否有 pending。  
无工具 + 有正文 → `model_done`。  
只对机器过不去的状态硬拦：进程还在跑、等批准、显式「必须运行 X」且从未成功过。

这已经对齐 Codex / OpenCode。回执只服务**当前**这一轮，不再开法官轮。

### D. 停时由运行时执行一次验收计划（推荐，但需要约束）

对齐 Claude Code Stop hook 的**内核**，但做成内置、有界、可审计的 D′：

1. 默认：无工具 + 有正文 → 模型提出结束。
2. 先完成空响应、截断、正文嵌入工具、实现任务从未调用工具等一次性恢复；这些不是验收门控。
3. 若存在运行中进程、待审批操作或用户必须介入的状态，等待或 `pause`，不进入验收。
4. 若本任务改过工程文件，且验收结果已过期，通过**正常工具执行链**运行一次确定的验收计划。
5. 计划全部 exit 0 → `model_done + completed`；失败 → 把精简失败输出注入模型，**只续一轮**。
6. 已经续过仍失败 → 停止循环并标记 `failed`；无法执行显式验收 → `paused`；没有可靠验收计划 → `completed_unverified`。
7. 问答、纯阅读、仅解释现有代码等无副作用任务直接结束，不自动运行命令。

这里的“一次”指**一次门控机会 / 一个验收计划**，不等于只跑一条命令。用户若明确要求七条命令全部成功，计划就包含七条命令，或者包含一个语义等价、可追踪到这七项的聚合脚本。

验收必须沿用现有命令工具的沙箱、审批、超时、取消、输出截断和 telemetry，不能由 `CompletionGate` 直接起子进程。仓库脚本也是任意代码执行，不能因为名字叫 `test` / `build` 就绕过策略。

过没过以真实完成状态和 **exit code** 为准，不依赖模型自述。`TaskAcceptanceTracker` 可以继续展示过程进度，但不得把启发式解析出的每个反引号变成硬阻塞位。

### E. 必须调用 `submit` / `attempt_completion` 才结束

SWE-bench 类 agent 常用。聊天产品里模型会忘调或早调，体验差于「写完正文即停」。

**不作为主路径。**

## 6. 最终建议：D′，循环对齐 C

```text
模型发 tool call  → 执行，喂回结果
        ↓
模型只写正文     → 前置恢复？(空响应 / 截断 / 嵌入工具 / 实现任务尚未执行)
                      ├─ 是 → 对应机制最多恢复一次
                      └─ 否 → 硬状态？(进程运行中 / 审批 / 需用户介入)
                                ├─ 是 → await 或 pause
                                └─ 否 → 有工程修改且验收已过期？
                                          ├─ 否 → model_done
                                          └─ 是 → 通过正常工具链执行一次验收计划
                                                    ├─ 全绿 → model_done + completed
                                                    ├─ 无计划 → model_done + completed_unverified
                                                    ├─ 不可执行 → paused
                                                    └─ 失败 → 注入输出，续一次
                                                               ├─ 后续绿 → completed
                                                               └─ 仍失败 → failed（停止但不伪装成功）
```

原则：

1. **模型拥有结束提议权**；运行时只因确定性硬状态或过期验收做一次有界延迟。
2. **质量闸是确定性的**（停时跑命令），不是 LLM 法官，也不是 prompt 编译器。
3. **同一段工作只许顶一次**（对齐 `stop_hook_active`）。
4. **硬条件只认用户写明的句式**（「完成条件：必须 `node --check …`」），长文里的 `npm ci`、`README.md` 不当 7+N 个 required。
5. **停止循环与验收通过分开**：预算用尽可以停，但终态必须保留 `failed` / `paused` / `completed_unverified`。
6. 低风险改完未测：一次验收或 `completed_unverified` 即可；不要再创建第二套 Verification Gate。

`CompletionGate` 可收缩为：运行中操作、审批、用户拒绝、状态不确定的写操作，以及显式验收失败/不可执行。不要再消费「从全部反引号生成的条件数组」来否决 `model_done`。

### 6.1 验收命令从哪里来

按以下优先级生成一个 `VerificationPlan`：

1. **用户显式声明**：只识别严格句式，例如「完成条件：必须运行 `...`」或结构化 acceptance 字段。
2. **项目显式配置**：例如未来的 `harness.verify`，或仓库内受信配置列出的命令。
3. **安全默认项**：仅在项目类型明确、脚本存在且已通过工具策略时选择低副作用命令，例如 `npm test`。
4. **无可靠来源**：不猜命令、不用 `git diff` 代替，结束为 `completed_unverified`。

不要把所有反引号、所有 `package.json` scripts 或名字像 `test` / `build` 的脚本自动登记为 required。本项目的 `npm run build` 会执行 `bump-pack-version.mjs`，说明“构建命令”本身也可能产生修改；验证命令必须声明或探测其副作用，执行后若工作区再次变化，本次验证不能覆盖这些新变化。

建议计划至少包含：

```ts
interface VerificationPlan {
  id: string;
  source: 'user' | 'project' | 'runtime_default';
  commands: Array<{
    command: string;
    required: boolean;
    timeoutMs: number;
  }>;
  fingerprint: string;
}
```

`fingerprint` 由规范化后的命令、顺序、工作目录和相关配置共同生成。计划变化后，旧成功结果自动失效。

### 6.2 如何判断“验证已过期”

不要比较 `Date.now()`。时间戳无法可靠表达并行工具、同毫秒修改、checkpoint 恢复和时钟变化。

运行时维护单调版本：

```ts
interface VerificationFreshness {
  workspaceMutationVersion: number;
  verifiedMutationVersion?: number;
  verifiedPlanFingerprint?: string;
}
```

- 每次成功落地的工程修改，使 `workspaceMutationVersion + 1`。
- 验收计划全部成功时，记录当时的 `verifiedMutationVersion` 和 `verifiedPlanFingerprint`。
- 仅当版本相等且 fingerprint 相同，验证才是 fresh。
- 验收命令自身若修改工程文件，会产生新版本，因此刚完成的结果仍视为过期；这类命令不应作为默认验收，显式使用时应以 `completed_unverified` 或要求用户确认收尾。
- checkpoint 必须保存这些版本，恢复时不得用文件数组长度或 wall-clock 时间重建。

首版可以采用任务级版本，先保证正确性；以后再按文件/模块计算受影响范围，不在首版引入依赖图。

### 6.3 失败如何分类

失败不能一律硬拦，也不能全部忽略：

- **只读探测失败**（例如错误的 `git diff` 参数）：模型已说明时允许结束，不污染验收状态。
- **显式 required 验收失败**：注入一次；仍失败则 `failed`。
- **默认软验收失败**：注入一次；仍失败则 `failed`，但明确标注是运行时选择的命令。
- **写操作部分失败或结果状态不确定**：`pause` 或 `failed`，不能用后续无关成功解除。
- **同 scope 的后续成功明确覆盖失败**：解除该失败。
- **用户拒绝 / 策略阻止**：不重试，`paused`，向用户说明未执行项。

运行中进程不是立即要求用户介入的理由。若它由 Harness 发起，应先在既有预算内 await / poll；只有超时、审批或环境阻塞才 `pause`。

### 6.4 注入给模型的失败回执

续跑消息只包含：

- 哪个验收命令失败；
- exit code；
- 最后若干行相关 stderr/stdout；
- 已经使用收尾续跑预算；
- 要求修复后只跑相关验证，不能用目录列表或 `git diff` 冒充。

不重复完整对话、工具 schema、成功命令的大段输出。第二次无工具结束时不再注入同一失败，但按真实状态返回 `failed`。

### 6.5 与现有恢复机制的边界

以下机制保留，并在 Completion Gate 之前执行：

- `finishReason=length` 的截断恢复；
- 空响应 / reasoning-only 恢复；
- 正文嵌入工具调用的 native function-calling 恢复；
- 实现类任务从未调用工具时的一次 `noToolExecutionRecovery`；
- 压缩后失忆恢复。

这些机制处理协议异常或明显未开始执行，不消费验收计划的“一次续跑”预算。每类机制仍必须有独立上限，不能互相重置形成组合死循环。

### 6.6 终态语义

- `completed`：没有硬阻塞；需要验收时，fresh 的验收计划全部成功。
- `completed_unverified`：有修改，但没有可靠验收计划，或用户没有要求且选择不追加验证。
- `paused`：等待审批、用户输入、外部环境，或显式验收当前不可执行。
- `failed`：required/运行时验收失败且一次恢复预算已用完，或写操作失败后状态不可接受。
- `interrupted`：资源上限、超时或用户中断。

`model_done` 是循环停止原因，不等价于 `completed`。最终事件和 UI 必须同时展示 stop reason 与 completion status，不能把 `model_done + failed` 折叠成普通成功。

## 7. 明确不做什么

- 不要为了收尾再打一轮「是否结束」的 LLM。
- 不要把完整对话、工具 schema、命令全文再塞一遍；回执保持短。
- 不要默认开启会无限 block 的 Stop hook。
- 不要在 Completion Gate 内直接起子进程或绕过 ToolGate / 审批。
- 不要按时间戳判断验证是否覆盖最后一次修改。
- 不要把「不再续跑」写成 `completed`；失败可以停止，但必须保留失败终态。
- 不要自动执行有副作用的 `build` / migration / snapshot 命令。
- 不要用 `git diff`、列目录、`node -e` 代替验收命令（续跑文案已禁止，停时跑测试则根本不会走到这一步）。

## 8. 和现有文档的关系

`Harness-L2与Gate工作逻辑.md` 写过：

- 用户明确要求验证 → required，必须有证据。
- 用户未说明 → 一次低成本观察，门控不硬拦。
- 额外观察是软行为，不创建第二套 Verification Gate。

fusion 事故违反的是后两条：推断出的反引号被升级成 required。本文把那份原则收回到和 Codex/CC 兼容的循环上，并用「停时执行一次确定的验收计划」补用户真正要的「过了就能结束」。

落地时建议另开实现任务，按顺序：

1. 先从收尾路径拿掉启发式 `TaskAcceptanceTracker` 硬拦，保留 UI/进度展示。  
2. 保留现有前置恢复；无工具正文在无硬状态时默认提出结束。  
3. 引入 `VerificationPlan`、命令来源优先级和工具链执行适配。  
4. 引入 mutation version + plan fingerprint，替代时间戳新鲜度。  
5. 接入一次验收续跑预算和准确的 completed / unverified / paused / failed 终态。  
6. 最后做 fusion-06 回放、单元测试和跨平台命令测试。

## 9. 落地验收标准

实现任务至少覆盖以下场景：

1. 长 prompt 中的路径、公式、标识符和普通反引号不会成为 required 条件。
2. 模型在已完成且验证 fresh 时输出正文，立即 `model_done + completed`，不追加 LLM 轮次。
3. 修改发生在成功验证之后，停手时只执行一次验收计划。
4. 七条显式 required 命令必须全部成功；只成功一条不能完成。
