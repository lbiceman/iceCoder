# 执行透明层（侧边栏形态）与设置开关设计

> 作者视角：Cursor / Claude Code 产品设计师
>
> 本文为 iceCoder **执行透明层（Execution Transparency Layer，ETL）** 的 **UI 形态升级 + 用户开关** 设计稿。
>
> 它不重造后端：ETL 的运行时（generator / tracker）、WebSocket 事件流、会话恢复、冰豆桥联已在
> [`docs/requirement/执行透明-finish.md`](./执行透明-finish.md) 落地。本文只做两件事：
>
> 1. 把当前「锚定冰豆的悬停气泡（popover）」升级为图示的 **右侧常驻侧边栏**；
> 2. 在 **设置** 里增加一个用户可控的 **总开关 + 偏好项**，决定是否显示透明层。
>
> 编码起点请直接看 §「落地建议与实现顺序」。

## 1. 设计目标（Why）

当前 ETL 的可见入口是冰豆底部一行摘要 + 悬停/点击展开的 popover（`src/public/js/chat-execution-plan.js`）。
它「轻」，但有三个体验缺口：

- **信息一闪即逝**：popover 靠 hover 触发、失焦即收，用户无法「常驻盯着 AI 在干嘛」。
- **维度单一**：只展示执行计划步骤，看不到 LLM 当前动作、工具调用明细、上下文、状态快照、日志。
- **不可预期**：面板位置随视口夹紧漂移，长任务下缺少稳定的「工作台」感。

产品目标是给用户一个 **可常驻、可信任、可回溯** 的「AI 工作透明面板」，对齐 Cursor / Claude Code 的心智：

- **看得见计划**：任务被拆成 N 步，当前第几步、下一步是什么，一目了然。
- **看得见过程**：LLM 当前动作、工具调用、上下文读写、状态快照，分 Tab 可查。
- **看得见代价**：Token 用量、工具调用次数、耗时，常驻在 footer。
- **可关可开**：默认不打扰重度用户；愿意看的人一键常驻，偏好持久化。

> 非目标：不改后端事件语义、不改冰豆核心 canvas、不强制所有用户都看到面板（**默认关闭**，尊重现有极简体验）。

> 🔴 **架构红线（详见 §14）**：透明层是纯 **Observer**，只消费事件、不影响事件。任何渲染 / Timeline / Drawer / Tooltip 异常都**必须降级为空 UI**，**绝不允许中断或影响 Harness / LLM / Tool / TaskGraph / Supervisor 的运行**。

### 3.1 面板容器

- 桌面端：聊天主区 **右侧常驻** `<aside id="exec-transparency-panel">`，默认宽 `360px`（可拖拽 320–480px，记忆到 localStorage）。
- 头部：标题「执行透明层」+ **唯一按钮：最小化（`—`）**。右上角**只保留最小化**，不再有 `×` 关闭按钮（是否显示透明层完全由设置开关决定，见 §4）。
- **最小化 ↔ 宠物形态**：点击最小化，面板收起为**宠物形态**（聊天页冰豆宠物）；**双击宠物**重新展开透明面板。这是展开/收起的唯一入口。
- 面板与主聊天区是 **并排 flex 布局**，面板出现时聊天区自适应收窄，不覆盖内容（区别于当前 popover 的浮层遮挡）。
- 冰豆（fixed canvas）**位置不变**，与面板共存；最小化后冰豆即作为「已收起」的入口与状态兜底。

### 3.2 顶部会话状态栏（①）

在聊天主区顶部新增/复用一根状态条，承载「这次会话/任务」的元信息：

| 字段 | 来源 | 示例 |
|------|------|------|
| 会话标题 + 工作目录 | 现有会话 store | `android学习` · `.../work/android` |
| 模式 | `execution_mode_*` 事件（`adaptive` / `forced`） | `模式：自适应` / `模式：强制执行` |
| 状态 | plan 进度 + stopReason | `运行中` / `已完成` / `已暂停` / `失败` |
| 暂停/继续 | 复用现有中断能力（若存在） | `⏸ 暂停` |

> 状态条是 ETL 面板的「锚」：点击「状态」区可展开/收起右侧面板，替代旧的 `#status-turn` hover 逻辑。

### 3.3 Tab 分区（面板主体）

| Tab | 内容 | 数据来源（复用现有事件） |
|-----|------|--------------------------|
| **执行流**（默认） | 当前步骤卡片 + 执行计划步骤列表 + LLM 当前动作 + 时间轴 | `execution_plan_init/update`、`task_graph_*`、`tool_call`/`tool_result`（推导动作，**不含 reasoning**） |
| **工具调用** | 时间线：每次工具名、入参摘要、结果/耗时、成功/失败 | `tool_call` / `tool_result` / `tool_progress` / `tool_output` / `tool_denied` |
| **上下文** | 已读文件、已改文件、执行的命令、最近诊断 | `repo-context.ts` 的 `RepoContextSnapshot`（经 `session_updated` 拉快照） |
| **状态快照** | `TaskStateSnapshot`：goal / intent / phase / verification 状态 | `src/types/runtime-snapshot.ts`（`GET /api/sessions/:id/plan` 同源扩展） |
| **日志** | 原始事件流（含 `memory_event` / `compaction`），可过滤/复制 | telemetry / WS step 原始流 |

### 3.6 LLM 当前动作（Current Activity）

> ⚠️ **重要澄清（给实现者）**：本区块 **不是** Chain of Thought / 思维链。iceCoder **不展示任何推理过程**：
> - 不展示推理过程（no reasoning process）
> - 不展示思维链（no chain of thought）
> - 不展示 reasoning（不订阅、不渲染 `reasoning_stream_delta`）
>
> 这里 **只展示一条**「LLM 此刻在做什么」的**动作状态短语**，与"模型在想什么"无关。

- **一次只显示一条**当前动作，实时更新、随任务推进替换（不堆叠历史、不逐 token 刷屏）。
- 文案长度建议 **20~40 字**，由 **当前 TaskGraph 节点阶段 + 最近工具事件** 确定性推导（见下表）。
- 示例：
  - `正在分析项目结构...`
  - `正在等待工具返回（read_file）...`
  - `正在生成修改方案...`
  - `正在验证结果...`
- 受设置项「显示 LLM 当前动作」控制；关闭时整块隐藏。

**动作文案映射（基于现有事件，零后端改动、无 reasoning）**

| 触发（`HarnessStepEvent` / TaskGraph 节点） | 当前动作文案 |
|------|------|
| 活动节点 `phase=context` 且 `running` | `正在分析项目结构...` |
| 已发 `tool_call`、对应 `tool_result` 未到 | `正在等待工具返回（{toolName}）...` |
| 活动节点 `phase=editing` 且 `running` | `正在生成修改方案...` |
| 活动节点 `isVerification` 且 `running` | `正在验证结果...` |
| `final` | `正在整理结论...` |

> 数据仅取 `tool_call.toolName`、`tool_result` 的到达、以及 `TaskGraphNodeView.phase/status`；**不读取任何 reasoning / thinking 文本内容**。

**为什么这样设计（Why）**

- **避免误导信任**：思维链是可被"编造"的自然语言，展示它会让用户误以为看到了模型的"真实想法"，反而放大噪音、削弱信任。
- **合规与隐私**：不暴露 reasoning，既规避各模型供应商对 CoT 展示的限制，也避免把中间推理泄露给终端用户。
- **稳定可预期**：动作状态由确定性的事件/阶段推导，"一次一条、可预期"，比逐 token 刷思维链更适合**常驻**面板。
- **低开销**：不订阅高频 reasoning delta，仅在节点/工具状态变化时更新一次，几乎无渲染压力。

### 3.7 时间轴（Timeline）

面板底部、footer 之上常驻一条**时间轴**，让用户对「这次任务花了多久、每一步发生在什么时刻、哪一步最耗时」有清晰、具体的时间感知（区别于步骤列表只给相对耗时）。

```
▸ 时间轴                                       [绝对时间 ▾] [仅步骤 ▾]
 14:24:01                                            现在 14:24:42
   ●───────●─────●──────────◍··········○········○
   理解     分析   检查        执行工具    分析SDK  生成方案
   2.1s     4.3s   1.8s       ⏱3.2s(运行) 等待中   等待中
 └────────────────── 总时长 00:41 ──────────────────┘
```

**设计要点**

- **横向刻度**：左端为任务开始绝对时间（`plan.createdAt` / 首个 `startedAt`），右端为「现在」（运行中）或结束时刻（完成时定格）。节点间距按真实耗时**按比例映射**，一眼看出耗时长短。
- **节点 = 事件**：默认每个 `TaskGraphNodeView` 一个节点（起点用 `startedAt`，终点用 `endedAt`）；提供粒度切换「仅步骤 / 步骤+工具调用」——后者把 `tool_call`/`tool_result` 也打点，颗粒更细。
- **节点状态**：复用 §3.5 状态色 —— `done` 实心 ●、`running` 脉冲 ◍、`pending` 空心 ○、`failed` 红叉、`skipped` 灰点。已完成段用实线，未来段用虚线。
- **绝对/相对切换**：右上角切换「绝对时间(14:24:03) / 相对时间(+02.1s)」，偏好记忆到 localStorage。
- **悬停 tooltip**：hover 节点显示「步骤标题 · 开始 14:24:03 · 结束 14:24:05 · 用时 2.1s」；点击节点滚动定位到 §3.5 对应步骤并高亮。
- **总时长条**：底部一根汇总条显示任务总时长（`最后 endedAt - 首个 startedAt`，运行中则到「现在」），与 footer 的「时间」一致。
- **溢出处理**：步骤多时时间轴横向可滚动，并默认吸附到「当前步骤」；窄面板下自动退化为**竖向时间线**（节点从上到下，左侧时间戳、右侧标题+耗时），避免横向拥挤。

**数据来源（复用现有字段，零后端改动）**

| 字段 | 取值 |
|------|------|
| 节点起/止时刻 | `TaskGraphNodeView.startedAt` / `endedAt`（`task-graph.ts` 在 `startCurrentNode`/`completeCurrentNode`/`skipCurrentNode` 写入，经 `task-graph-view-mapper.ts` 映射） |
| 任务起点 | `TaskGraphView.createdAt`（= `graph.createdAt`） |
| 最近更新/现在 | `TaskGraphView.updatedAt` / `Date.now()`（运行中每秒刷新 running 节点宽度） |
| 历史校验 | 可选参考 `graph.nodeHistory[]`（每节点 `{startedAt,endedAt,retries,error}`，仅服务端持有，非必需） |
| 工具粒度节点 | `tool_call` / `tool_result` 事件的**前端接收时刻**（`HarnessStepEvent` 未携带工具级绝对时间戳，故只能兜底） |

> 说明：**节点(步骤)级时间精确**，来自后端 `startedAt/endedAt`；**工具级时间为前端接收时刻的近似**。因此时间轴默认粒度为「仅步骤」，切到「步骤+工具」时对工具节点标注为近似时间。

### 3.7.1 Timeline 中的 Supervisor 事件（监管层，重点）

iceCoder 有 **Runtime Supervisor（L2 监管层 / 双模机制）**。当它介入执行——进入 **Takeover（接管）**、**Recovery（恢复）**、**Correction（纠偏）**——Timeline 必须**明显体现**，让用户一眼看出「这里 AI 卡住了 / 被监管层接管并重新规划」。这是与普通 Tool / 步骤节点**并列的一级事件**。

> 兼容前提：Supervisor 事件是 **叠加** 在既有 Timeline 上的一类特殊节点。**若本次任务没有任何 Supervisor 事件，Timeline 与 §3.7 完全一致，不受影响。**

#### 1) UI 设计

- **一级事件节点**：Supervisor 事件在时间轴上占据一个**独立的醒目节点**（不是挂在某个 Tool 节点下的角标），与普通步骤节点同级排布，按发生时刻插入到时间线相应位置。
- **醒目图标**：统一用 `⚠` 前缀；节点比普通节点略大、加 Warning 描边。
- **一句话摘要**：节点主标题为事件类型（`Supervisor 接管` / `开始恢复` / `重新规划` / `继续执行`），副标题为一行原因摘要。
- **可展开查看原因**：点击节点展开详情——完整 `primaryReasonHuman` + 触发信号列表（中文映射）+ 轮次 `round`；再次点击收起。默认收起，不干扰主视图。
- **面板顶部监管状态条（复用现有实现）**：当处于接管中（`executionMode==='forced'`）时，面板顶部常驻一条 Warning 横幅「⚠ 监管接管中 · {原因}」，复用现有 `.exec-plan-mode-banner`（`renderExecutionModeBanner`，见 `chat-execution-plan.js`）；退出接管后横幅消失。
- **不影响普通 Tool 节点**：普通节点的颜色、状态、耗时渲染完全不变；Supervisor 节点只是**额外插入**。

#### 2) 数据来源（全部来自现有 `HarnessStepEvent`，零后端改动）

| Timeline 事件 | 来源事件 / 字段 | 判定 |
|------|------|------|
| `⚠ Supervisor 接管`（Takeover） | `execution_mode_enter`，`executionMode.executionMode === 'forced'` | 进入强制/接管段 |
| `开始恢复`（Recovery Started） | `execution_mode_enter`，`enteredBy` 含 `recovery_pending` 或 `checkpoint_resumed` | 恢复触发 |
| `重新规划`（Re-plan） | `task_graph_branch`（分支切换）/ 新一轮 `task_graph_init` | 图被重建/切换分支 |
| `继续执行`（Resume） | `execution_mode_exit` | 监管交还模型 |
| 原因文案 | `executionMode.primaryReasonHuman`（如「连续 N 轮无进展」） | 直接展示 |
| 触发信号（展开项） | `executionMode.enteredBy: ModeSignal[]`（如 `tool_failure`/`recovery_pending`/`branch_switched`） | 用现有中文映射 `MODE_SIGNAL_LABELS` |
| 轮次 | `executionMode.round` | 展开项显示 |
| 发生时刻 | 事件前端接收时刻（对齐节点级 `startedAt/endedAt`） | 插入时间线位置 |

> 说明：`ExecutionModeTelemetryPayload`（`src/types/supervisor.ts`）已随 `execution_mode_enter/exit` 抛到前端，`chat-execution-plan.js` 现有 `applyExecutionModeEvent` / `MODE_SIGNAL_LABELS` 已在消费它。本设计只是把这些事件**额外投影到 Timeline**，不新增任何事件类型或接口。

#### 3) 状态颜色

| 事件类别 | 颜色（现有 CSS 变量） | 图标 |
|------|------|------|
| Supervisor 接管 / 纠偏 | **Warning** `--warning` / `--warning-light` | `⚠` |
| 开始恢复 / 重新规划 | Warning（略浅）`--warning` 描边 + 虚线连接 | `↻` |
| 继续执行（交还） | 恢复常规色 `--accent`，节点回到普通样式 | `▸` |
| 普通步骤 / 工具 | 维持 §3.5 原色，不改 | — |

> Warning 色专用于「监管介入段」，与普通 `running`（`--accent` 蓝）、`failed`（`--danger` 红）在视觉上区分开：红=某步失败，橙=监管层介入。

#### 4) Timeline 示例（竖向，含 Supervisor 段）

```
14:22:11  ● 分析项目                     完成 2.1s
             │
14:22:15  ● read_file                    完成 0.6s
             │
14:22:16  ⚠ Supervisor 接管            [展开 ▾]   ← Warning 橙
             │   原因：连续 3 轮无进展
             │   信号：工具失败 + 恢复待定  · 第 6 轮
             │
14:22:16  ↻ 开始恢复（Recovery）                   ← Warning 橙
             │
14:22:18  ↻ 重新规划（Re-plan）                    ← 虚线，图被重建
             │
14:22:19  ▸ 继续执行                                ← 交还模型，恢复常规色
             │
14:22:31  ● 生成解决方案                 完成 12s
             │
14:22:33  ● 完成                         ✅
```

> 无 Supervisor 事件时，上面的 `⚠ / ↻ / ▸` 三类节点不出现，时间线就是纯步骤节点（同 §3.7）。

#### 5) 实现建议

- **纯前端投影**：在 `chat-execution-plan-bridge.js` 收到 `execution_mode_enter/exit`、`task_graph_branch` 时，除现有的 banner 逻辑外，**追加一条 Timeline 事件记录**（`{ kind:'supervisor', subtype, reasonHuman, signals, round, ts }`）到面板本地的时间线数组。
- **渲染分层**：Timeline 渲染时把 supervisor 事件与步骤节点按 `ts` 归并排序后统一出图；supervisor 节点走独立模板（Warning 色 + 图标 + 可展开），普通节点模板不动。
- **展开态**：原因/信号复用现有 `MODE_SIGNAL_LABELS` / `DEGRADED_LABELS` 中文映射（`chat-execution-plan.js` 已有），无需新增文案表。
- **降级/兜底**：`enteredBy` 为空或 `primaryReasonHuman` 缺失时，退化为「⚠ 监管接管」单行，不报错。
- **零协议改动**：不新增 WS 事件、不新增 REST 接口；一切基于既有 `execution_mode_*` / `task_graph_branch`。

### 4.2 开关项定义

| 键 | 类型 | 默认 | 说明 |
|----|------|------|------|
| `showTransparencyPanel` | 开关 | **关** | 主开关。关闭时聊天页完全不挂载面板 DOM（退回冰豆底部摘要）。 |
| `panelDefaultExpanded` | 开关 | 开 | 主开关开启时，新会话/刷新后面板是**默认展开**还是**默认最小化为宠物形态**（需双击宠物展开）。 |

| `showTimeline` | 开关 | 开 | 是否显示底部时间轴区块。 |

### 4.3 存储与生效

- **前端偏好**（推荐）：统一存到 `localStorage['ICE_ETL_PREFS']`（JSON），并 **兼容迁移** 旧键
  `localStorage['ICE_PLAN_PANEL']`（`'0'` → `showTransparencyPanel=false`）。
  - 选前端存储的原因：这是「显示偏好」，跨设备不必强一致，且免后端改动，切换即时生效（无需重启/新会话）。
- **可选后端持久化**：若需跨设备同步，扩展 `GET/PATCH /api/config`（与 `skipPermissionChecks` 同模式），
  字段 `executionTransparency: { enabled, ... }`。本期默认走 localStorage，后端为后续增量。

### 4.4 与服务端能力开关的关系（两层门控）

```
ICE_ENABLE_EXECUTION_PLAN (env, 服务端能力)   →  connected.features.executionPlan
        │  决定是否产生 execution_plan_* 事件
        ▼
用户设置 showTransparencyPanel (前端偏好)     →  决定是否渲染面板
        │
        ▼
最终显示 = features.executionPlan && showTransparencyPanel
```

设置项的三态呈现：

| `features.executionPlan` | `showTransparencyPanel` | 设置页表现 | 聊天页表现 |
|--------------------------|--------------------------|------------|------------|
| false（服务端未启用） | 任意 | 开关 **禁用** + 提示「当前服务未启用执行透明层能力」 | 不显示 |
| true | false | 开关可用，关 | 不显示（仅冰豆摘要） |
| true | true | 开关可用，开 | 显示右侧面板 |

## 5. 交互与状态

- **最小化（唯一收起入口）**：点击头部 `—`，面板收起为**宠物形态**（聊天页冰豆宠物）。没有 `×` 关闭按钮——是否显示透明层由 §4 设置开关决定。
- **双击宠物展开**：双击聊天页冰豆宠物，重新展开透明面板。
  - **受设置开关门控**：仅当设置主开关 `showTransparencyPanel` 为**开**时，双击宠物才展开；**设置为关时双击宠物无任何效果**（面板本就不挂载）。
  - **最终门控**：`features.executionPlan && showTransparencyPanel` 才允许展开（见 §4.4）。
- **删除宠物原「双击恢复默认位置」逻辑**：聊天页冰豆宠物原来的「双击回到默认锚点」交互（`src/public/js/session-pet.js` 的 `initPetDrag` 中 `dblclick` → `clearCustomPosition()`）**予以移除**，双击语义改为「展开透明面板」。宠物拖拽移动位置的能力保留；仅去掉双击复位。
- **桌面宠物不受影响**：本节所有改动仅针对**聊天页内的冰豆宠物**（`session-pet.js`，`enableDrag` 默认 true）。**桌面悬浮宠物（`pet-floating-page.js` / Electron 独立窗口，`enableDrag:false`，不进入 `initPetDrag`）的交互与双击行为完全不变**，且**无论透明层展示或关闭，桌面宠物都不受影响**。
- **Tab 记忆**：记住上次所选 Tab（localStorage）。
- **实时更新**：复用现有 `applyPatch` 差量更新，仅变化的 step 重渲染，避免抖动。
- **空态**：无 plan（如纯问答 `question` intent）时，面板显示「本次为问答，无执行计划」，不空白。
- **完成态**：`progress===100` 时当前步骤卡片转为「已完成 · 用时 mm:ss」，计划列表全绿，footer 定格。
- **失败态**：`failed` 步骤红色，展开显示 `error`；顶部状态栏 `状态：失败`。

## 14. Observer 约束（隔离与容错 · 硬性红线）

> 本章为**不可违反的架构红线**。执行透明层（ETL）在系统中的角色是纯粹的 **Observer（只读观察者）**：只能**消费**事件，**绝不能影响**事件的产生与 Agent 的运行。

### 14.1 单向数据流

```
Harness / LLM / Tool / TaskGraph / Supervisor
        │  （只出不进：HarnessStepEvent 单向推送）
        ▼
   WebSocket step 流  ──►  ETL（面板 / Timeline / Drawer / Tooltip）
                              ✗ 无任何反向通道
```

- ETL **只订阅**既有 WS `step` 事件与 `GET /api/sessions/:id/plan` 等**只读**端点。
- ETL **不得**发送任何会改变执行的消息（本期无反向控制通道；未来若有也须走独立显式通道，不得混入渲染路径）。
- ETL 的任何 UI 状态（展开 / 最小化 / 切 Tab / hover）**都不回传**、不改变 Harness / LLM / Tool / TaskGraph / Supervisor 的任何状态。

### 14.2 进程级隔离（天然保证）

- 运行时（Harness / LLM / Tool / TaskGraph / Supervisor）在 **Node 后端进程**；ETL 在**浏览器前端**。
- 前端**整页崩溃或卡死，后端照常运行**：WS 推送为 fire-and-forget，后端不 `await` 前端渲染、不因前端断开而阻塞或报错。
- 因此「透明层挂了 → Agent 停了」在架构上不成立；下面的容错是为了保证**前端自身**也优雅降级。

### 14.3 容错：任何异常降级为空 UI

以下所有场景**必须 `try/catch` 兜底，吞掉异常并降级为空/占位 UI，绝不 `throw` 冒泡到事件分发器，绝不中断 Agent 执行**：

| 失败点 | 降级行为 |
|------|------|
| 渲染失败（`setPlan` / `applyPatch` / step 节点） | 跳过该项，其余照常；整体失败则清空列表显示占位 |
| Timeline 出错 | 隐藏时间轴区块，保留面板其余部分 |
| Drawer / 面板崩溃 | 关闭并卸载面板，回退**宠物形态**；后端与事件流不受影响 |
| Tooltip / 展开项异常 | 关闭该浮层，节点回退为纯文本 |
| Supervisor 投影异常 | 丢弃该条 Timeline 事件，不影响主流程 |

### 14.4 实现硬性规则（对编码者）

- **事件处理器全包裹**：`chat-execution-plan-bridge.js` 的 `onStep` 与 `chat-execution-plan.js` 的 `setPlan` / `applyPatch` / `renderTimeline` / `renderStep` / `pushSupervisorTimelineEvent` 等入口，**每个都以 `try { … } catch (e) { console.warn(...); /* 降级 */ }` 包裹**。
- **不阻塞 WS 分发**：处理器**同步、快速返回**，不 `await` 长任务；单个 listener 抛错不得中断 `chat-websocket.js` 的 `step` 分发循环，不得连累其他 listener 与后续事件。
- **无副作用回传**：渲染路径中禁止任何 `fetch` / WS `send` 写操作（只读拉取快照除外）。
- **致命兜底（错误边界）**：面板顶层捕获不可恢复错误时 `minimize()` 收为宠物形态并 `console.warn`，**不弹错、不中断会话**。
- **验收**：注入构造异常（畸形 plan / 缺字段 patch / 超大 Timeline / tooltip 抛错）时，Agent 执行与事件流**零中断**，UI 仅表现为对应区块降级或空。
