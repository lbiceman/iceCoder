## 2. 模块逐一分析

### 2.1 Harness 核心（src/harness，100+ 文件）

**状态：最成熟模块。** L1 Execution Mode（free↔forced）+ L2 RecoverySupervisor（takeover/handoff/drift）均已实现（`src/harness/supervisor/` 13 文件），并有 checkpoint / compaction / task-graph / verification-gate / sub-agent / branch-budget / recovery 等完整子体系。测试覆盖 40+ 文件，是仓库测试密度最高的区域。

**薄弱点：**
- `harness.ts` 单文件 912 行，承担消息预处理、压缩、LLM 调用、工具执行、状态转换，重构候选。
- 规格文档 [`运行时后续优化.md`](./requirement/运行时后续优化.md) 明确列出 **Benchmark 落盘 / Eval Runner 扩展 / Learning 层 / 验收自动化** 四个未启动项（前置依赖是双模附录 B 验收）。

### 2.2 记忆系统（src/memory/file-memory，34 文件）

**状态：功能完备。** memory-recall（LLM select+rank）、memory-dream（LLM 主动整理）、eviction、scanner、secret-scanner、index-health、telemetry、多级记忆均有实现，前端 `memory-page.js` 提供图谱可视化。

**薄弱点（测试日志实证）：**
- Dream 在无 LLM 时抛 `TypeError: Cannot read properties of null (reading 'chat')`（`memory-dream.ts:896`，测试 `memory-dream.test.ts:873` 已覆盖降级但日志暴露错误路径）。
- `persistState` 在临时目录场景报 ENOENT（rename 竞态，`memory-dream.ts` 的 atomic-write 在目录不存在时失败）。

### 2.3 LLM 层（src/llm，13 文件）

**状态：够用但单一。** OpenAI 适配器 + `openai-responses-bridge` + `vision-fallback` + 指数退避重试（`llm-adapter.ts` 完整）。provider 通过 `provider-adapter-config.ts` 归一化。

**薄弱点：**
- 全部指向 OpenAI 兼容系 API，**无本地模型 / 非 OpenAI 厂商适配器**；多模型仅是「逗号分隔的多 model 列表」（README 截图），不是多 provider 路由。
- `llm-adapter.ts` 372 行内聚重试 + token 跟踪 + 委托，逻辑可拆。

### 2.4 工具系统（src/tools，30+ 文件）

**状态：仓库最厚实的模块之一。** shell 安全体系尤其完整：sandbox / command-parser / host-guard / runtime-classifier / cd-parser / inline-script-advisory / process-kill（含 PowerShell 进程树）。另有 background-task-manager、session-shell-control、懒加载 `tool-offering-selector`（本会话刚落地，含 sticky 记忆）。

**薄弱点：** 无明显缺口；shell 相关工具数量多、职责边界需靠文档维持。

### 2.5 Web 层（src/web + routes 13 组）

**状态：功能齐全。** chat-ws.ts 统一 PC/移动（token 区分），路由覆盖 config / tools / remote / sessions / upload / memory-export / memory-files / memory-dream / skills / mcp-status / workspace-browse / supervisor-events。

**薄弱点：**
- **`chat-ws.ts` 2998 行**是仓库最大单文件：WS 生命周期 + harness 驱动 + 事件广播 + 断点恢复 + 任务队列 + shell 协管全挤在一个文件。
- 前端 `chat-page.js` 2700 行同理，是第二大单文件。

### 2.6 前端（src/public/js，43 文件）

**状态：完整可用。** 原生 JS 无框架，chat 主流程 / 执行透明层（ETL）/ 冰豆宠物 / 移动 H5 shell / 设置页（general/model/mcp）齐全。

**薄弱点：**
- 纯 JS 无类型、无模块打包，43 个文件靠 `window.X` 全局约定耦合。
- 前后端偏好逻辑**重复**：`etl-prefs.js`（前端 sanitize）与 `main-config-ice-etl-prefs.ts`（后端 sanitize）各维护一份 `DEFAULT_ICE_ETL_PREFS`，改字段需双处同步（本会话已踩过：新增 `taskDoneNotification` 改了 4 个文件）。

### 2.7 会话层 / MCP / CLI（src/session 5 文件 · src/mcp 10 文件 · src/cli）

**状态：够用。** session 有 task-queue / pending-note / shell-collab / tool-policy / bg-tasks-store；MCP 有 manager / client / reload / persist / 后台启动 / 运行时上下文；CLI 有 start / cli / web / run / tools / mcp / config 七个子命令。

**薄弱点：**
- ~~`src/core/orchestrator.ts` 仅 40 行，只剩 getter，注释「原多智能体流水线已移除」——**空心模块**，`outputDir/sessionDir` 标注「预留」但无使用方。~~ **已处理（2026-08-10）**：删除无消费方的 `OrchestratorConfig`/`config` 字段/`getConfig()`，类回归纯 holder（LLM + FileParser）职责；同步清理 `src/index.ts`、`src/cli/bootstrap.ts` 构造调用与测试。

### 2.8 桌面端（desktop/src，17 文件）

**状态：可交付。** 主窗 / 系统托盘 / 悬浮冰豆（embedded↔floating）/ 系统通知（含任务完成通知 + 点击聚焦 + 前台抑制）/ server 子进程管理 / Windows toast 快捷方式。

**薄弱点：**

## 5. 推荐下一步（按优先级）

### P0 — 短期高收益（1–2 天）
1. **失败通知前端接入**：主进程已完成 `success=false` 分支（title/body 均就绪），前端 `maybeNotifyTaskDone` 增加失败场景（`error`/`length`/`circuit_breaker`）调用即可，附 2 个单测。改动面最小、直接完成规格 §3.2 预留。
2. **chat-ws.ts 拆分**：把 2998 行按「连接管理 / harness 驱动 / 事件广播 / 恢复逻辑 / 工具上下文」拆 5 个模块。纯重构、行为不变、风险可控，为后续所有 Web 功能铺路。

### P1 — 中期（3–5 天）
3. **运行时优化第一步：Benchmark 落盘 + Eval Runner 扩展**：规格文档已冻结（`运行时后续优化.md` §3 指标表），双模已实现，落地 `supervisor-benchmark.jsonl` 与 CSV 导出，接 `scripts/eval-runner.ts`。这是从「能跑」走向「可度量」的关键一步。
4. **桌面端测试补齐**：为 `pet-window-manager` / `server-process` / `paths` / `port-utils` 补单测（参考已建成的 `task-done-notify.test.ts` 纯函数抽取模式——先抽纯逻辑再测）。

### P2 — 长期（方向性）
5. **Learning 层（Agent OS 第一步）**：基于 EventTimeline + eval 结果生成 `supervisor-config.json` 建议补丁（人工合并，不做运行时静默改配置）——规格已写死约束。
6. **LLM 多 provider**：抽象 `ProviderAdapter` 接口已存在，接一个本地模型（如 Ollama/llama.cpp）验证接口通用性。
7. **前端工程化**：43 个原生 JS 引入极简打包（esbuild）+ 类型注释，逐步消除 `window.X` 全局耦合。
